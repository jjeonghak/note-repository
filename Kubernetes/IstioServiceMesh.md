# 서비스 메시
데이터 플레인과 컨트롤 플레인으로 구성된 아키텍처  
데이터 플레인은 애플리케이션 계층 프록시를 사용해서 네트워킹 트래픽 관리  
컨트롤 플레인은 프록시 관리  
특정 프로그래밍 언어에 의존하지 않고 애플리케이션-네트워킹 기능을 외부에서 구축  

<br>

### 서비스 지향 아키텍처 전환 고려사항
장애가 격리 경계를 넘어 확산하는 것을 방지  
환경 변화에 대응할 수 있는 서비스 구축  
부분적 장애 상태에서도 동작하는 시스템 구축  
끊임없이 변화하고 발전하는 전체 시스템 상태 파악  
시스템의 런타임 동작 제어 불가 문제  
시스템 변경의 위험성 낮추기  
시스템 구성 요소에 대한 접근 정책 강제  

<br>

### 복원력 있는 서비스 상호작용
- 클라이언트 측 로드 밸런싱: 클라이언트에게 엔드포인트 제공
- 서비스 디스커버리: 특정 논리적 서비스의 주기적 갱신되는 정상 엔트포인트 목록 탐색 메커니즘
- 서킷 브레이커: 오동작 서비스에 일정 시간 부하 차단
- 격벽: 클라이언트 리소스 사용량을 명시적 임계값으로 제한(커넥션, 스레드, 세션 등)
- 타임아웃: 서비스 호출 시 요청, 소켓, 활성 등에 시간 제한 적용
- 재시도: 실패한 요청 재시도
- 재시도 예산: 재시도에 제한 적용
- 데드라인: 요청에 응답 유효 기간 지정

<br>

## 인프라를 통한 관리

### 애플리케이션 라이브러리로 관리
복원력을 구축할 책임이 각 애플리케이션에 있다면 처리 분산으로 인한 중앙 병목 해결 가능  
하지만 새 서비스를 도입하려 한다면 다른 서비스에서 내린 구현 결정에 제약을 받음  
어떤 경우에는 각 프레임워크/언어 조합에 상응하는 유사 대체품을 찾지 못할 가능성도 존재  
여러 프로그래밍 언어와 프레임워크에서 라이브러리를 소수로 유지하는 난이도가 높음  

<br>

### 엔보이 프록시

<img width="650" height="400" alt="envoy_proxy" src="https://github.com/user-attachments/assets/9d342fa1-50a0-4ab5-818c-714dec5357a6" />

엔보이는 애플리케이션 프로세스 외부에서 구현되는 서비스 프록시  
언어나 프레임워크에 명시적 의존성 없이도 재시도, 타임아웃, 서킷브레이커, 로드 밸런싱 등 네트워킹 관심사 구현  
초당 요청 수, 실패 횟수, 서킷 브레이커 이벤트 등과 같은 네트워킹 메트릭 수집  

<br>

<img width="650" height="350" alt="sidecar" src="https://github.com/user-attachments/assets/659fa367-b253-4710-9ad0-845a7dd8058b" />

또한 서비스 프록시는 분산 트레이싱 스팬을 수집해 특정 요청이 수행한 모든 단계를 연결 가능  
각 단계 별 소요 시간을 확인하고 잠재적 병목 현상 탐색 가능  
애플리케이션 코드 한 줄 변경 없이 들어오는 모든 트래픽이 프록시를 거침  
엔보이 같은 서비스 프록시는 애플리케잇ㄴ의 모든 인스턴스와 함께 단일 최소 단위로 배포 가능

## 서비스 메시

<img width="700" height="400" alt="service_mesh" src="https://github.com/user-attachments/assets/0b0d30d1-f67a-48ab-8e18-7135d74b18c9" />

서비스 메시란 애플리케이션 대신 프로세스 외부에서 투명하게 네트워크 트래픽을 처리하는 분산형 애플리케이션 인프라  
데이터 플레인은 모든 프래픽을 처리하고 관찰하는 곳, 메시를 거쳐가는 트래픽을 설정하고 제어하는 책임  
컨트롤 플레인은 데이터 플레인의 동작을 설정, 운영자가 네트워크 동작을 조작할 수 있도록 API 엔드포인트 노출  

<br>

## 이스티오 서비스 메시
이스티오는 서비스 메시의 오픈소스 구현체이며 구글, IBM, 리프트가 주도  
이스티오를 사용하면 애플리케이션은 자신이 서비스 메시의 일부임을 인지할 필요 없음  
애플리케이션이 외부와 통신할 때는 항상 이스티오가 대신 네트워킹 처리  
이스티오는 데이터 플레인과 엔보이 프록시를 사용  
원래는 쿠버네티스에서 실행할 목적으로 구축됐지만, 배포 플랫폼에 구애받지 않는 관점으로 작성(오픈시프트, 가상머신 등)  

<br>

<img width="700" height="550" alt="istio_service_mesh" src="https://github.com/user-attachments/assets/0ed00131-d149-410c-9b22-499d022942f1" />

1. 트래픽은 이스티오 인그레스 게이트웨이를 통해 메시 외부 클라이언트에서 클러스터로 들어옴
2. 트래픽이 서비스 프록시를 통과(타임아웃, 메트릭 수집, 보안 강제 등 적용 가능)
3. 요청이 다양한 서비스를 거치며 이스티오의 서비스 프록시는 다양한 단계에서 요청을 가로채고 라우팅 결정
4. 컨트롤 플레인(`istiod`)은 라우팅, 보안, 텔레메트릭 수집, 복원력 처리 설정
5. 요청 메트릭은 주기적으로 다양한 수집 서비스로 전송(예거, 집킨 등)

<br>

이스티오는 기본적으로 보안이 활성화  
네트워킹 경로의 양 끝단을 제어하기 때문에 트래픽을 투명하게 암호화 가능  
서비스가 상호 TLS 사용 가능하도록 키 및 인증서 발급, 설치, 로테이션을 관리  
이 밖에 할당량, 속도 제한, 조직 정책 구현 가능  

<br>

### 서비스 메시와 엔터프라이즈 서비스 버스 관계
서비스 지향 아키텍처(`SOA`)의 엔터프라이즈 서비스 버스(`ESB`)는 애플리케이션이 그 존재를 알지 못함  
서비스 메시 또한 애플리케이션에게 투명하지만 ESB가 하던 모든 일을 맡지 못함  

<br>

<img width="700" height="500" alt="esb" src="https://github.com/user-attachments/assets/e5bb535f-ca1a-4d86-b9ad-d47d8a20c2dc" />

- ESB는 중앙화된 배포/구현
- ESB는 애플리케이션 네트워킹과 서비스 중재 문제를 혼합
- ESB는 복잡한 독점 벤더 소프트웨어를 기반으로 하는 경우가 많음

서비스 메시의 역할은 오직 애플리케이션 네트워킹 문제에만 해당  
복잡한 비즈니스 변환, 오케스트레이션 등은 서비스 메시의 일이 아님  
또한 데이터 플레인은 프록시를 애플리케이션에 붙이는 형태로 분산하기 때문에 ESB의 SPOF 혹은 병목 지점 문제 제거  

<br>

<br>

### 분산 아키텍처에 적합한 경우

<img width="700" height="400" alt="istio_layer" src="https://github.com/user-attachments/assets/42550802-c758-4be9-8cb3-3427ad02a9f2" />

이스티오는 어떤 배포 자동화 도구를 사용해야 하는지 규정하거나 침해하지 않음  
또한 어떤 비즈니스 로직도 구현하거나 대체하지 않음  
배포 플랫폼과 애플리케이션 코드 사이의 복잡한 네트워킹 코드를 애플리케이션과 분리하는 역할  

<br>

### 서비스 메시 단점
서비스 메시를 사용하면 요청 경로에 미들웨어, 프록시 추가 필수  
프록시가 익숙하지 않다면 오히려 디버깅하기 어려움  
메시 내에 서비스가 많을수록 메시의 가치가 높아지지만 잘못 설정한 경우 여러 서비스에 악영향  
서비스 메시가 새로운 계층이 되므로 전체 아키텍처의 복잡성이 증가
