# 신뢰성 있는 데이터 전달

## 신뢰성 보장
신뢰성에 대해서는 대개 보장(`guarantee`)을 거론, 보장이란 서로 다른 상황에서도 시스템이 지킬 것이라고 보장되는 행동  
신뢰성 보장은 관계형 데이터베이스가 보편적으로 지원하는 표준 신뢰성 보장인 ACID  
아래는 카프카가 제공하는 보장  
- 파티션 안의 메시지들 간에 순서를 보장, 먼저 쓰여진 메시지는 이후 메시지보다 오프셋이 낮음
- 클라이언트 메시지는 모든 인-싱크 레플리카 파티션에 쓰여진 뒤에야 커밋된 것으로 간주
- 커밋된 메시지는 최소 1개 이상 작동 가능한 레플리카에 남아 있다면 유실되지 않음
- 컨슈머는 커밋된 메시지만 조회 가능

<br>

## 브로커 설정
파티션 별로 다수의 레플리카를 유지한다는 특성이 카프카 신뢰성 보장의 핵심  
메시지 저장 신뢰성 관련된 브로커 설정 매개변수는 세 가지 존재  
토픽 단위에서 신뢰성 트레이드오프 제거가 가능, 신뢰성이 필요한 토픽과 아닌 토픽을 분류 가능  

<br>

### 복제 팩터
토픽 단위 설정은 `replication.factor`, 자동 생성 토픽은 브로커 단위 설정 `default.replication.factor`에 저장  
이미 존재하는 토픽도 레플리카 재할당 툴을 사용해서 추가 또는 삭제 가능(복제 팩터 변경 가능)  
토픽에 복제 팩터를 설정할 경우 아래 요소 고려  
- 가용성: 레플리카 수가 많을수록 가용성 증가
- 지속성: 파티션 복사본이 많을수록 데이터 유실 가능성 감소
- 처리량: 레플리카가 추가될 때마다 브로커간 트래픽(복제 트래픽) 증가
- 종단 지연: 쓰여진 메시지를 컨슈머가 조회하려면 모든 인-싱크 레플리카 복제가 필수, 레플리카 수가 많을수록 지연 발생
- 비용: 레플리카 수가 많을수록 저장소와 네트워크 비용 증가

<br>

### 언클린 리더 선출
해당 설정은 브로커 단위에서만 가능, 기본값은 `unclean.leader.election.enable=false`  
언클린 리더 선출은 데이터 유실과 일관성 깨짐의 위험성이 존재, 하지만 가용성 높음  
만약 작동 불능에 빠진 리더 외 인-싱크 레플리카가 존재하지 않는 경우 아래 상황 발생  
- 예전 리더(마지막 인-싱크)가 복구될 때까지 해당 파티션은 오프라인
- 언클린 리더 선출 설정이 된 경우 새 리더가 예전 리더에 쓰여진 메시지 유실 및 컨슈머 오프셋 혼란(뒤섞인 채 조회)

<br>

### 최소 인-싱크 레플리카
토픽과 브로커 단위 모두 `min.insync.replicas` 설정 가능  
만약 인-싱크 레플리카가 작동 불능에 빠진 경우 가용성과 일관성 사이에서 트레이드 오프 발생  
해당 설정보다 인-싱크 레플리카가 없는 경우 프로듀서의 쓰기 요청에 `NotEnoughReplicasException` 응답  
하지만 컨슈머는 계속해서 존재하는 데이터 조회 가능(읽기 전용)  

<br>

### 레플리카 인-싱크 상태 유지
`zookeeper.session.timeout.ms` 설정은 브로커가 주키퍼로 하트비트 전송을 멈출 수 있는 최대 시간  
해당 값은 무작위적 변동에 영향을 받지 않을 만큼 높고, 적시에 브로커 다운을 탐지할 수 있을 만큼 낮게 설정  
`replica.lag.time.max.ms` 설정보다 더 오랫동안 리더로부터 데이터를 읽지 못하면 아웃-오브-싱크 상태  
해당 값은 컨슈머가 메시지를 읽을 수 있게 되는데 걸리는 최대값으로 영향을 준다는 점 명심  

<br>

### 디스크 저장
카프카는 세그먼트 교체시와 재시작 직전에만 메시지를 디스크로 플러시  
그 외의 경우는 리눅스 페이지 캐시 기능에 의존  
브로커가 디스크에 더 자주 메시지를 저장하도록 `flush.messages`, `flush.ms` 설정 가능  

<br>

## 신뢰성 있는 시스템에서 프로듀서 사용
가장 높은 신뢰성 설정을 브로커에 적용하더라도 프로듀서 역시 신뢰성 있도록 설정 필요  
- 신뢰성 요구 조건에 맞는 올바른 `acks` 설정 사용
- 설정과 코드 모두에서 올바른 에러 처리

<br>

### 응답 보내기
프로듀서는 아래 세 가지 응답 모드 중 하나 선택 가능
- `acks=0`: 프로듀서가 네트워크로 메시지 전송한 시점에 성공적으로 쓰여진 것으로 간주
- `acks=1`: 리더가 메시지를 받아서 파티션 데이터 파일에 쓴 직후 응답 또는 에러를 보내는 것 의미
- `acks=all`: 리더가 모근 인-싱크 레플리카의 메시지 조회를 대기한 후 응답 또는 에러를 보내는 것 의미

<br>

### 프로듀서 재시도 설정
프로듀서 에러 처리는 프로듀서가 자동 처리하는 에러와 개발자가 처리해야 하는 에러 두 가지로 구분  
프로듀서는 재시도 가능한 에러는 처리 가능(`LEADER_NOT_AVAILABLE` 가능, `INVALID_CONFIG` 불가능)  
일반적으로 메시지 유실하지 않는 가장 좋은 방법은 재시도 수를 기본 설정값(`MAX_INT`)으로 두고 전송 포기 대시 시간을 지정  
전송 실패 메시지를 재시도하는 것은 결과적으로 메시지 중복 위험 존재  
재시도와 주의 깊은 에러 처리는 각 메시지가 `최소 한 번` 저장을 보장하지만 `정확히 한 번`은 보장 못함  

<br>

### 추가적인 에러 처리
프로듀서에 탑재된 재시도 기능 이외에도 개발자 입장에서는 다른 종류의 에러 처리 필요  
- 메시지 크기에 관련 또는 인가 관련 브로커 에러
- 메시지가 브로커에 전송되기 전에 발생한 에러(직렬화 과정 에러 등)
- 프로듀서가 모든 재전송 시도 소진 또는 가용 메모리 오버플로우 에러
- 타임아웃

<br>

## 신뢰성 있는 시스템에서 컨슈머 사용
컨슈머는 일관성이 보장되는 데이터만 조회, 컨슈머는 어느 메시지까지 조회했는지를 추적  
컨슈머는 메시지를 배치 단위로 조회, 배치별로 마지막 오프셋을 확인, 브로커에게 다른 메시지 배치 요청
