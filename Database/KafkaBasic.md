# 카프카
모든 애플리케이션은 데이터를 생성하고 데이터의 모든 부분은 의미가 존재  
이러한 데이터의 의미를 알기 위해서는 데이터를 생성된 곳에서 분석할 수 있는 곳으로 옮길 필요성 존재  

<br>

## 발행/구독 메시지 전달
발행/구독 패턴의 특징은 전송자가 데이터를 보낼 때 수신자로 보내지 않는다는 것  
대신 전송자는 어떤 형태로든 메시지를 분류해서 보내고 수신자는 분류된 메시지를 구독  
대개 발행된 메시지를 전달받고 중계해주는 중간 브로커가 존재  

<br>

## 카프카 입문
카프카는 위의 문제를 해결하기 위해 고안된 메시지 발행/구독 시스템  
분산 커밋 로그 혹은 분산 스트리밍 플랫폼으로 칭함  

<br>

### 메시지와 배치
카프카에서 데이터의 기본 단위는 메시지, 메시지는 단순히 바이트 배열이기 때문에 특정한 형식이나 의미 없음  
메시지는 키 메타데이터를 포함가능한데 키 역시 특별한 의미 없는 바이트 배열이지만 보통 파티션을 결정하기 위해 사용  
가장 간단한 방법은 키값에 일정한 해시값을 생성한 후 이 값을 토픽의 파티션 수로 나눈 나머지 값을 이용해서 파티션 저장  

카프카는 효율성을 위해 메시지를 배치 단위로 저장, 배치는 그저 같은 토픽의 파티션에 쓰여지는 메시지 집합  
네트워크 상에서 발생하는 막대한 오버헤드를 줄이기 위해 메시지를 배치 단위로 모아서 전송  
배치는 효율적인 데이터 전송과 저장을 위해 약간의 처리 능력을 들여서 압축되는 경우 존재  

<br>

### 스키마
카프카 입장에서 메시지는 단순한 바이트 배열이지만 일정한 구조를 부여하는 것을 권장  
JSON, XML 같이 읽기 편한 스키마도 있지만 호환성 유지 기능이 떨어지기 때문에 아파치 에이브로(`Avro`)를 선호  
에이브로는 조밀한 직렬화 형식을 제공하고 메시지 본체와 스키마를 분리하기 때문에 스키마 변경에 유연  

메시지 쓰기와 읽기 작업을 분리하기 위해서 일관적인 데이터 형식이 중요  
잘 정의된 스키마를 공유 저장소에 저장함으로써 카프카는 두 버전 형식을 동시에 지원하도록 하는 작업 없이도 메시지 처리 가능  

<br>

### 토픽과 파티션

<img width="650" height="300" alt="kafka_topic_and_partition" src="https://github.com/user-attachments/assets/52027d6c-768f-40d6-a6ab-7ed2aadf1b26" />

카프카에 저장되는 메시지는 토픽 단위로 분류, 가장 비슷한 개념으로 데이터베이스 테이블과 파일시스템 폴더  
토픽은 다시 여러 개의 파티션으로 나눔, 파티션에 메시지가 쓰여질 때는 추가만 가능하고 읽을 때는 맨 앞부터 순서대로  
토픽 안의 메시지 전체에 대해 순서는 보장되지 않으며 단일 파티션 안에서만 순서가 보장  
각 파티션이 서로 다른 서버에 저장 가능하며 하나의 토픽이 여러 개의 서버로 수평적으로 확장 가능  

<br>

### 프로듀서와 컨슈머
프로듀서는 새로운 메시지를 생성, 발행/구독 모델에서는 발행자라고 부름  
기본적으로 프로듀서는 메시지를 쓸 때 토픽에 속한 파티션들 사이에 고르게 나누어 쓰도록 구성  
어떠한 경우에는 프로듀서가 특정한 파티션을 지정해서 메시지 작성, 주로 메시지 키값을 이용한 파티셔너를 사용해서 구현  

컨슈머는 메시지를 조회, 발행/구독 모델에서는 구독자라고 부름  
컨슈머는 1개 이상의 토픽을 구독해서 여기에 저장된 메시지들을 각 파티션에 쓰여진 순서대로 조회  
메시지의 오프셋을 기록함으로써 어느 메시지까지 읽었는지를 유지  
주어진 파티션의 각 메시지는 고유한 오프셋을 가지며 뒤에 오는 메시지가 반드시 앞 메시지보다 큰 오프셋을 보유  

<br>

<img width="650" height="300" alt="kafka_consumer_group" src="https://github.com/user-attachments/assets/439b1a1f-f189-432d-b549-4992331f1510" />

컨슈머는 컨슈머 그룹의 일원으로 작동, 컨슈머 그룹은 토픽에 저장된 데이터를 읽어오기 위해 협업하는 하나 이상의 컨슈머로 구성  
컨슈머 그룹은 각 파티션이 하나의 컨슈머에 의해서만 읽히도록 유지  
컨슈머에서 파티션으로의 대응 관계를 컨슈머의 파티션 소유권이라고 칭함  

<br>

### 브로커와 클러스터
카프카 브로커는 클러스터의 일부로 작동하도록 설계  
하나의 클러스터 안에 여러 개의 브로커가 포함 가능하며 그중 하나의 브로커는 클러스터 컨트롤러 역할  
컨트롤러는 파티션을 브로커에 할당하거나 장애 발생 브로커를 모니터링하는 등의 관리 기능 담당  

<br>

<img width="650" height="400" alt="kafka_paartition_replication" src="https://github.com/user-attachments/assets/4134e328-51c9-47c6-9fb3-5a6c88d83be9" />

파티션은 클러스터 안의 브로커 중 하나가 담당하며 그 브로커를 파티션 리더로 칭함  
복제된 파티션은 파티션의 팔로워로 칭하며 메시지를 중복 저장함으로써 리더 브로커에 장애 발생시 팔로워 중 하나가 리더 역할  
카프카 핵심 기능 중 일정 기간 동안 메시지를 보존하는 기능 존재  
특정 기간 동안 또는 파티션 크기 임계값까지만 보존하는 방식으로 보존  

<br>

### 다중 클러스터
설치된 카프카가 확장됨에 따라 다수의 클러스터 운용이 효과적일 수 있음  
- 데이터 유형별 분리
- 보안 요구사항을 충족하기 위한 격리
- 재해 복구를 대비한 다중 데이터센터

<br>

<img width="650" height="450" alt="kafka_multi_cluster" src="https://github.com/user-attachments/assets/b9aa7494-0c24-440a-b8d7-b03dcc8c2cc5" />

기본적으로 복제 메커니즘은 다중 클러스터 사이가 아닌 하나의 클러스터 안에서만 작동하도록 설계  
다른 클러스터로 복제하기 위해서 미러메이커(`MirrorMaker`) 툴 포함  
근본적으로 미러메이커도 단지 큐로 연결된 카프카 컨슈머와 프로듀서에 불과

## 환경 설정
설치된 카프카가 원활하게 작동하려면 몇 가지 환경 설정 필수  

<br>

### 주키퍼

<img width="450" height="300" alt="kafka_zookeeper" src="https://github.com/user-attachments/assets/93ebdcbb-2769-41c6-8e52-1d8f8f7e7ce5" />

카프카 클러스터의 메타데이터와 컨슈머 클라이언트에 대한 정보를 저장하기 위해 아파치 주키퍼 사용  
설정 정보 관리, 이름 부여, 분산 동기화, 그룹 서비스를 제공하는 중앙화된 서비스  

<br>

주키퍼는 고가용성을 보장하기 위해 앙상블(`ensemble`)이라 불리는 클러스터 단위로 작동  
부하 분산 알고리즘 때문에 앙상블은 홀수 개의 서버를 가지며 요청에 응답하려면 쿼럼의 과반 이상이 작동 필수  
각 서버는 공통된 설정 파일을 사용해야하며 데이터 디렉토리에 자신의 ID 번호를 지정하는 `myid` 파일 보유 필수  

<br>

```properties
tickTime=2000
dataDir=/var/lib/zookeeper
clientPort=2181
initLimit=20
syncLimit=5
server.1=zoo1.example.com:2888:3888
server.2=zoo2.example.com:2888:3888
server.3=zoo3.example.com:2888:3888
```

위 설정은 앙상블 안의 모든 서버 내역 역시 정의  
`server.{X}={hostname}:{peerPort}:{leaderPort}` 형식으로 정의  
- X: 서버의 ID(myid 정의 값)
- hostname: 서버의 호스트명 또는 IP 주소
- peerPort: 앙상블 안의 서버들이 서로 통신할 때 사용하는 TCP 포트
- leaderPort: 리더를 선출하는데 사용되는 TCP 포트 번호

<br>

### 핵심 브로커 매개변수
1. `broker.id`: 모든 카프카 브로커는 정수값 식별자를 보유
2. `listeners`: `{protocol}://{hostname}:{port}` 형태로 정의
3. `zookeeper.connect`: 브로커의 메타데이터가 저장되는 주키퍼의 위치를 지정, `{hostname}:{port}/{path}` 형태로 정의
4. `log.dirs`: 모든 메시지를 로그 세그먼트 단위로 묶어서 지정된 디스크 디렉토리에 저장
5. `num.revovery.threads.per.data.dir`: 설정 가능한 스레드 풀을 사ㅛㅇ해서 로그 세그먼트 관리
6. `auto.create.topics.enable`: 토픽 자동 생성 여부
7. `auto.leader.rebalance.enable`: 토픽의 리더 역할이 균둥하게 분산되도록 리더 리밸런싱 여부
8. `delete.topic.enable`: 클러스터의 토픽을 임의 삭제 방지 여부
9. `num.partitions`: 새로운 토픽이 생성될 때 몇 개의 파티션을 갖게 되는지 결정

<br>
