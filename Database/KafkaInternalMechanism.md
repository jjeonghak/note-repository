# 카프카 내부 메커니즘

## 클러스터 멤버십
현재 클러스터의 멤버인 브로커들의 목록을 유지하기 위해 아파치 주키퍼 사용  
각 브로커는 설정 파일에 정의되었거나 아니면 자동 생성된 고유 식별자를 사용  
브로커 프로세스는 시작될 때마다 주키퍼에 `Ephemeral` 노드 형태의 ID를 등록  
컨트롤러를 포함한 카프카 브로커들은 브로커가 등록되는 주키퍼의 `/brokers/ids` 경로를 구독해서 알림을 받음  
만약 특정한 브로커가 완전히 유실되어 동일한 ID를 가진 새로운 브로커를 투입할 경우 곧바로 유실된 브로커의 자리를 대신  

<br>

## 컨트롤러
일반적인 카프카 브로커의 기능에 더해서 파티션 리더 선출 역할을 추가로 수행  
클러스터에서 가장 먼저 시작되는 브로커는 주키퍼의 `/controller`에 `Ephemeral` 노드를 생성해서 컨트롤러로 등록  
다른 브로커 역시 해당 위치에 노드 생성을 시도하지만 이미 존재하기 때문에 예외를 반환  

컨트롤러가 삭제될 경우 와치를 통해 다른 브로커들이 알아차리며 컨트롤러 노드 생성 시도  
이때 성공한 브로커가 다음 컨트롤러가 되며 조건적 증가 연산을 통해 증가된 에포크 값을 전달하며 새로운 와치를 생성  
이전 컨트롤러가 재가동해도 다른 브로커들은 낮은 에포크 번호의 메시지를 무시  

브로커가 컨트롤러가 되면 주키퍼로부터 최신 레플리카 상태 맵을 조회  
이 적재 작업은 비동기로 수행되며 지연을 줄이기 위해 여러 단계로 요청을 나누어 주키퍼로 전송  
파티션 수가 매우 많은 클러스터에서는 적재 작업이 몇 초씩 걸림  

브로커가 클러스터를 나가면 컨트롤러는 해당 브로커가 리더를 맡고 있는 모든 파티션에 대해 새로운 브로커 할당  
새로운 상태를 주키퍼에 쓴 후 새로 리더가 할당된 파티션의 모든 브로커에 `LeaderAndISR` 요청을 보냄  
해당 요청은 파티션들에 대한 새로운 리더와 팔로워 정보를 포함  

새로 리더가 된 브로커 각각은 쓰기 혹은 읽기 요청을 처리, 팔로워들은 새 리더로부터 메시지 복제  
클러스터의 모든 브로커는 전체 브로커와 레플라키의 맵을 포함하는 `MetadataCache` 보유  
컨트롤러는 모든 브로커에 리더십 변경 정보를 포함하는 `UpdateMetadata` 요청을 보내서 각각 캐시 업데이트
