# 카프카 내부 메커니즘

## 클러스터 멤버십
현재 클러스터의 멤버인 브로커들의 목록을 유지하기 위해 아파치 주키퍼 사용  
각 브로커는 설정 파일에 정의되었거나 아니면 자동 생성된 고유 식별자를 사용  
브로커 프로세스는 시작될 때마다 주키퍼에 `Ephemeral` 노드 형태의 ID를 등록  
컨트롤러를 포함한 카프카 브로커들은 브로커가 등록되는 주키퍼의 `/brokers/ids` 경로를 구독해서 알림을 받음  
만약 특정한 브로커가 완전히 유실되어 동일한 ID를 가진 새로운 브로커를 투입할 경우 곧바로 유실된 브로커의 자리를 대신  

<br>

## 컨트롤러
일반적인 카프카 브로커의 기능에 더해서 파티션 리더 선출 역할을 추가로 수행  
클러스터에서 가장 먼저 시작되는 브로커는 주키퍼의 `/controller`에 `Ephemeral` 노드를 생성해서 컨트롤러로 등록  
다른 브로커 역시 해당 위치에 노드 생성을 시도하지만 이미 존재하기 때문에 예외를 반환  

<br>

컨트롤러가 삭제될 경우 와치를 통해 다른 브로커들이 알아차리며 컨트롤러 노드 생성 시도  
이때 성공한 브로커가 다음 컨트롤러가 되며 조건적 증가 연산을 통해 증가된 에포크 값을 전달하며 새로운 와치를 생성  
이전 컨트롤러가 재가동해도 다른 브로커들은 낮은 에포크 번호의 메시지를 무시  

<br>

브로커가 컨트롤러가 되면 주키퍼로부터 최신 레플리카 상태 맵을 조회  
이 적재 작업은 비동기로 수행되며 지연을 줄이기 위해 여러 단계로 요청을 나누어 주키퍼로 전송  
파티션 수가 매우 많은 클러스터에서는 적재 작업이 몇 초씩 걸림  

<br>

브로커가 클러스터를 나가면 컨트롤러는 해당 브로커가 리더를 맡고 있는 모든 파티션에 대해 새로운 브로커 할당  
새로운 상태를 주키퍼에 쓴 후 새로 리더가 할당된 파티션의 모든 브로커에 `LeaderAndISR` 요청을 보냄  
해당 요청은 파티션들에 대한 새로운 리더와 팔로워 정보를 포함  

<br>

새로 리더가 된 브로커 각각은 쓰기 혹은 읽기 요청을 처리, 팔로워들은 새 리더로부터 메시지 복제  
클러스터의 모든 브로커는 전체 브로커와 레플라키의 맵을 포함하는 `MetadataCache` 보유  
컨트롤러는 모든 브로커에 리더십 변경 정보를 포함하는 `UpdateMetadata` 요청을 보내서 각각 캐시 업데이트  

<br>

### KRaft: 새로운 래프트 기반 컨트롤러
주키퍼 기반 컨트롤러로부터 탈피해서 래프트 기반 컨트롤러 쿼럼으로 옮겨가는 시도  
최신 버전의 카프카 클러스터는 전통적인 주키퍼 기반 컨트롤러와 KRaft 기반 컨트롤러 중 하나 선택해서 실행 가능  
아래와 같은 이유로 주키퍼에서 새로운 컨트롤러를 교체하기로 결정  
- 주키퍼에 메타데이터를 쓰는 작업은 동기지만 브로커 메시지 전송과 업데이트 받는 과정은 비동기
- 컨트롤러가 재시작될 때마다 주키퍼로부터 모든 브로커와 파티션에 대한 메타데이터를 읽어야 하는데 여전히 병목
- 메타데이터 소유권 관련된 내부 아키텍처가 그리 좋지 않음
- 주키퍼틑 그 자체로 분산 시스템, 카프카와 마찬가지로 운영을 위한 러닝 커브 존재

<br>

현재 아키텍처에서 주키퍼는 컨트롤러 선출과 클러스터 메타데이터 저장이라는 두 가지 주요한 기능 수행  
새로운 아키텍처에서 컨트롤러 노드들은 메타데이터 이벤트 로그를 관리하는 래프트 쿼럼 역할  
래프트 알고리즘을 사용해서 컨트롤러 노드들은 외부 시스템에 의존하지 않고 자체적으로 리더 선출 가능  
메타데이터 로그의 리더 역할을 하는 컨트롤러는 액티브 컨트롤러라고 부름  
액티브 컨트롤러는 브로커가 보낸 모든 호출을 처리하고 팔로워 컨트롤러들은 쓰여진 데이터들을 복제  

<br>

<img width="700" height="350" alt="kafka_kraft" src="https://github.com/user-attachments/assets/be7d5960-729a-4f2a-b135-a33969c4c36f" />

기존에 주키퍼 기반으로 사용중이었던 클러스터 업데이트는 브리지 릴리스 단계를 거처 업그레이드 가능  

<br>

## 복제
개별적인 노드에 필연적 장애가 발생할 수 밖에 없는 상황에서 신뢰성과 지속성을 보장하는 방식  
- 리더 레플리카: 각 파티션에 리더 역할을 하는 레플리카가 하나씩 존재
- 팔로워 레플리카: 리더 레플리카를 제외한 나머지, 리더 레플리카로부터 모든 메시지를 복제해서 최신 상태 유지

<br>

리더 레플리카는 각 팔로워 레플리카가 마지막으로 요청한 오프셋 값을 확인  
만약 팔로워가 일정 시간 이상 읽기 요청을 보내지 않거나 최근 메시지를 따라잡지 못하는 경우(`out-of-sync`) 리더 후보 제외  
반대로 지속적으로 최신 메시지를 요청하고 있는 인-싱크(`in-sync`) 레플리카만 파티션 리더 후보  

<br>

## 요청 처리
카프카 브로커가 하는 대부분의 일은 클라리언트, 파티션 레플리카, 컨트롤러가 파티션 리더에게 보내는 요청을 처리  
모든 요청은 아래와 같은 표준 헤더를 보유  
- 요청 유형: API 키
- 요청 버전: 서로 다른 버전의 클라이언트로부터 요청을 받아 각각의 버전에 맞는 응답
- Correlation ID: 각 요청에 붙는 고유한 식별자
- 클라이언트 ID: 요청을 보내는 애플리케이션 식별자

<br>

<img width="500" height="300" alt="kafka_request_process" src="https://github.com/user-attachments/assets/0c54971f-1781-439f-8aff-ecf594717075" />

브로커는 연결을 받는 각 포트별로 억셉터(`acceptor`) 스레드를 하나씩 실행  
억셉터 스레드는 연결을 생성하고 들어온 요청을 프로세서 스레드에 넘겨 처리  
네트워크 스레드는 클라이언트 연결로부터 들어온 요청을 요청 큐에 넣고 응답 큐에서 응답을 대기  

<br>

<img width="500" height="300" alt="kafka_metadata_request" src="https://github.com/user-attachments/assets/b373091c-187d-45cd-8864-a29ba1ce9a87" />

쓰기와 읽기 요청 모두 파티션의 리더 레플리카로 전송되어야 함  
다른 브로커가 쓰기 요청을 받은 경우 `Not a Leader for Partition` 에러로 응답  
카프카 클라이언트는 메타데이터 요청이라 불리는 요청을 사용해서 자신이 다루고자 하는 토픽들의 목록을 전송  
브로커는 해당 토픽들에 어떤 파티션이 존재하고 각 리더 레플리카를 명시하는 응답을 리턴  
클라이언트는 보통 해당 정보를 캐시해 두었다가 사용, 최신값 유지를 위해 새로운 메타데이터 요청 재시도  

<br>

### 쓰기 요청
리더 레플리카를 보유한 브로커는 해당 파티션 쓰기 요청을 받고 유효성 검증 시작  
- 데이터를 보내고 있는 사용자의 토픽에 대한 쓰기 권한 보유 여부
- 요청에 지정되어 있는 acks 설정값(0, 1, all 중 하나만 가능)
- acks all 경우 메시지를 안전하게 쓸 수 있을 만큼 충분한 인-싱크 레플리카 존재 여부

<br>

### 읽기 요청
클라이언트는 브로커에 토픽, 파티션, 오프셋 목록에 해당하는 메시지들을 요청  
클라이언트는 또한 각 파티션에 대해 브로커가 리턴할 수 있는 최대 데이터 양 지정, 반대로 리턴될 데이터의 양의 하한도 지정 가능  
요구한 데이터 양이 되지 않더라도 타임 아웃 설정으로 대기 시간 설정 가능  
카프카는 클라이언트에게 메시지를 보낼 때 제로카피(`zero-copy`) 최적화 사용  
다른 데이터베이스와 다르게 중간 버퍼를 거치지 않고 바로 네트워크 채널로 전송  

<br>

<img width="700" height="200" alt="kafka_consumer_insync_blocking" src="https://github.com/user-attachments/assets/d61c0fad-d50f-48ab-9861-28337ae4d3e8" />

충분한 수의 레플리카에 복제가 완료되지 않은 메시지는 불안전한 것으로 간주  
모든 인-싱크 레플리카에 쓰여지기 전까지 컨슈머는 해당 메시지들 조회 불가  
리더가 다운되는 상황에서 다른 레플리카가 리더 역할을 이어받는다면 해당 메시지들은 더 이상 카프카에 존재하지 않음  
컨슈머가 많은 수의 파티션을 폴링하는 경우 파티션 전체 목록을 요청마다 전송하고 받는 것은 매우 비효율  
오버헤드 최소화를 위해 읽기 세션 캐시를 사용, 컨슈머는 읽고 있는 파티션 목록과 그 메타데이터를 캐시하는 세션 생성  
세션을 생성한 후 모든 파티션 지정이 아닌 점진적 읽기 요청 가능  

<br>

## 물리적 저장소
카프카 기본 저장 단위는 파티션 레플리카  
파티션은 서로 다른 브로커들 사이에 분리 불가능, 같은 브로커의 서로 다른 디스크에 분할 저장도 불가능  

<br>

### 계층화된 저장소
카프카는 대량의 데이터를 저장하기 위한 목적으로 사용되고 있어서 아래 문제 발생
- 파티션별 저장 가능한 데이터 한도 존재
- 디스크와 클러스터 크기는 저장소 요구 조건에 의해 결정
- 클러스터 크기 변경에 대해 파티션의 크기가 클수록 클러스터 탄력성 감소

<br>

계층화된 저장소 기능에서는 클러스터의 저장소를 로컬과 원격 두 계층으로 분리  
로컬 계층은 현재 카프카 저장소 계층과 같이 로컬 세그먼트 저장(로컬 디스크 사용)  
원격 계층은 완료된 로그 세그먼트를 다른 저장소에 저장(S3 등 저장소 시스템 사용)  
계층별 다른 보존 정책 설정 가능(로컬 보존 기한은 짧게, 원격 보존 기한은 길게)  

<br>

계층화된 저장소 기능의 이중화된 구조 덕분에 클러스터의 메모리에 상관없이 저장소 확장 가능  
로컬 저장 데이터 양 감소에 따라 복구와 리밸런싱 과정에서 복사되는 데이터 양 역시 감소  
원격 계층에 저장되는 로그 세그먼트들은 브로커에 복원될 필요 없이 바로 클라이언트로 전달  

<br>

### 파티션 할당
파티션 할당은 브로커 갯수, 파티션 갯수, 복제 팩터에 영향을 받음  
- 레플리카들을 브로커에 가능한 고르게 분산
- 각 파티션에 대해 각각의 레플리카는 서로 다른 브로커에 배치
- 브로커에 랙 정보가 설정되어 있는 경우 파티션 레플리카들을 서로 다른 랙에 할당

<br>

브로커를 선택했다면 새 파티션을 저장할 디렉토리 결정, 해당 작업은 파티션별로 독립적 수행  
각 디렉토리에 저장되어 있는 파티션의 수를 센 후에 가장 적은 파티션이 저장된 디렉토리에 새 파티션 저장  
단 파티션을 브로커에 할당해 줄 때 사용 가능한 공간 또는 현재 부하 같은 것은 고려되지 않음  

<br>

### 파일 관리
카프카는 영구히 데이터를 저장하지 않음, 대신 각각의 토픽에 대해 보존 기한을 설정 가능  
큰 파일에서 메시지를 삭제하는 것은 시간이 오래 걸리기 때문에 파티션을 여러 개의 세그먼트로 분할  
각 세그먼트는 1GB 데이터 혹은 1주일치 데이터 중 작은 값으로 저장  
카프카가 파티션 단위로 메시지를 쓰는 만틈 각 세그먼트 한도가 다 차면 세그먼트를 닫고 새 세그먼트 생성  
현재 쓰고 있는 세그먼트는 액티브 세그먼트, 액티브 세그먼트는 어떠한 경우에도 삭제되지 않음  
세그먼트가 닫히기 전까지 데이터 삭제 불가  

<br>

### 파일 형식
각 세그먼트는 하나의 데이터 파일 형태로 저장, 파일 안에는 카프카 메시지와 오프셋이 저장  
네트워크를 통해 전달되는 형식과 디스크에 저장되는 형식을 통일(프로듀서가 보낸, 컨슈머로 보내지는 메시지 형식과 동일)  
카프카 메시지는 사용자 페이로드와 시스템 헤더 두 부분으로 구분, 사용자 페이로드는 키-밸류와 헤더 모음 포함  
카프카 프로듀서는 메시지를 메시지 배치 헤더를 포함해서 배치 단위로 전송  
- 메시지 형식의 현재 버전을 가리키는 매직 넘버
- 배치에 포함된 첫 번째 메시지 오프셋과 마지막 오프셋 차이
- 첫 번째 메시지 타임스탬프와 가장 큰 타임스탬프
- 바이트 단위로 표시된 배치 크기
- 배치를 받은 리더의 에포크 값
- 체크섬
- 서로 다른 속성 표기를 위한 16비트
- 프로듀서 ID, 프로듀서 에포크, 배치의 첫 번째 시퀀스 넘버
- 배치에 포함된 메시지 집합

<br>

### 압착
카프카의 보존 정책 중 삭제 보존 정책은 지정된 보존 기한보다 오래된 메시지를 삭제하고 압착 보존 정책은 최근값만 저장  
애플리케이션이 키-밸류를 모두 포함하는 메시지를 생성하는 토픽의 경우에만 압착 가능

카프카의 압착 기능이 활성화된 경우 브로커는 압착 매니저 스레드와 함께 다수의 압착 스레드 시작  
각 스레드는 전체 파티션 크기 대비 더티 메시지의 비율이 가장 높은 파티션을 골라 압착 후 클린 상태로 변환  
클리너 스레드는 파티션의 더티 영역을 읽어서 인-메모리 맵을 생성  

<br>

만약 가장 최근 메시지조차도 삭제하려면 해당 키값과 `null` 밸류를 갖는 메시지(툼스톤)를 전송  
클리너 스레드는 해당 메시지를 발견하면 압착 작업한 후 일정 기간이 지나면 삭제  
툼스톤 메시지를 컨슈머가 볼 수 있도록 시간을 주는 것은 툼스톤 메시지를 놓치고 나중에 데이터를 읽더라도 알 수 있도록 하기 위함
