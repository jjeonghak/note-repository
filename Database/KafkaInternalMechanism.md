# 카프카 내부 메커니즘

## 클러스터 멤버십
현재 클러스터의 멤버인 브로커들의 목록을 유지하기 위해 아파치 주키퍼 사용  
각 브로커는 설정 파일에 정의되었거나 아니면 자동 생성된 고유 식별자를 사용  
브로커 프로세스는 시작될 때마다 주키퍼에 `Ephemeral` 노드 형태의 ID를 등록  
컨트롤러를 포함한 카프카 브로커들은 브로커가 등록되는 주키퍼의 `/brokers/ids` 경로를 구독해서 알림을 받음  
만약 특정한 브로커가 완전히 유실되어 동일한 ID를 가진 새로운 브로커를 투입할 경우 곧바로 유실된 브로커의 자리를 대신  

<br>

## 컨트롤러
일반적인 카프카 브로커의 기능에 더해서 파티션 리더 선출 역할을 추가로 수행  
클러스터에서 가장 먼저 시작되는 브로커는 주키퍼의 `/controller`에 `Ephemeral` 노드를 생성해서 컨트롤러로 등록  
다른 브로커 역시 해당 위치에 노드 생성을 시도하지만 이미 존재하기 때문에 예외를 반환  

컨트롤러가 삭제될 경우 와치를 통해 다른 브로커들이 알아차리며 컨트롤러 노드 생성 시도  
이때 성공한 브로커가 다음 컨트롤러가 되며 조건적 증가 연산을 통해 증가된 에포크 값을 전달하며 새로운 와치를 생성  
이전 컨트롤러가 재가동해도 다른 브로커들은 낮은 에포크 번호의 메시지를 무시  

브로커가 컨트롤러가 되면 주키퍼로부터 최신 레플리카 상태 맵을 조회  
이 적재 작업은 비동기로 수행되며 지연을 줄이기 위해 여러 단계로 요청을 나누어 주키퍼로 전송  
파티션 수가 매우 많은 클러스터에서는 적재 작업이 몇 초씩 걸림  

브로커가 클러스터를 나가면 컨트롤러는 해당 브로커가 리더를 맡고 있는 모든 파티션에 대해 새로운 브로커 할당  
새로운 상태를 주키퍼에 쓴 후 새로 리더가 할당된 파티션의 모든 브로커에 `LeaderAndISR` 요청을 보냄  
해당 요청은 파티션들에 대한 새로운 리더와 팔로워 정보를 포함  

새로 리더가 된 브로커 각각은 쓰기 혹은 읽기 요청을 처리, 팔로워들은 새 리더로부터 메시지 복제  
클러스터의 모든 브로커는 전체 브로커와 레플라키의 맵을 포함하는 `MetadataCache` 보유  
컨트롤러는 모든 브로커에 리더십 변경 정보를 포함하는 `UpdateMetadata` 요청을 보내서 각각 캐시 업데이트  

<br>

### KRaft: 새로운 래프트 기반 컨트롤러
주키퍼 기반 컨트롤러로부터 탈피해서 래프트 기반 컨트롤러 쿼럼으로 옮겨가는 시도  
최신 버전의 카프카 클러스터는 전통적인 주키퍼 기반 컨트롤러와 KRaft 기반 컨트롤러 중 하나 선택해서 실행 가능  
아래와 같은 이유로 주키퍼에서 새로운 컨트롤러를 교체하기로 결정  
- 주키퍼에 메타데이터를 쓰는 작업은 동기지만 브로커 메시지 전송과 업데이트 받는 과정은 비동기
- 컨트롤러가 재시작될 때마다 주키퍼로부터 모든 브로커와 파티션에 대한 메타데이터를 읽어야 하는데 여전히 병목
- 메타데이터 소유권 관련된 내부 아키텍처가 그리 좋지 않음
- 주키퍼틑 그 자체로 분산 시스템, 카프카와 마찬가지로 운영을 위한 러닝 커브 존재

<br>

현재 아키텍처에서 주키퍼는 컨트롤러 선출과 클러스터 메타데이터 저장이라는 두 가지 주요한 기능 수행  
새로운 아키텍처에서 컨트롤러 노드들은 메타데이터 이벤트 로그를 관리하는 래프트 쿼럼 역할  
래프트 알고리즘을 사용해서 컨트롤러 노드들은 외부 시스템에 의존하지 않고 자체적으로 리더 선출 가능  
메타데이터 로그의 리더 역할을 하는 컨트롤러는 액티브 컨트롤러라고 부름  
액티브 컨트롤러는 브로커가 보낸 모든 호출을 처리하고 팔로워 컨트롤러들은 쓰여진 데이터들을 복제

## 복제
개별적인 노드에 필연적 장애가 발생할 수 밖에 없는 상황에서 신뢰성과 지속성을 보장하는 방식  
- 리더 레플리카: 각 파티션에 리더 역할을 하는 레플리카가 하나씩 존재
- 팔로워 레플리카: 리더 레플리카를 제외한 나머지, 리더 레플리카로부터 모든 메시지를 복제해서 최신 상태 유지

<br>

리더 레플리카는 각 팔로워 레플리카가 마지막으로 요청한 오프셋 값을 확인  
만약 팔로워가 일정 시간 이상 읽기 요청을 보내지 않거나 최근 메시지를 따라잡지 못하는 경우(`out-of-sync`) 리더 후보 제외  
반대로 지속적으로 최신 메시지를 요청하고 있는 인-싱크(`in-sync`) 레플리카만 파티션 리더 후보  

<br>

## 요청 처리
카프카 브로커가 하는 대부분의 일은 클라리언트, 파티션 레플리카, 컨트롤러가 파티션 리더에게 보내는 요청을 처리  
모든 요청은 아래와 같은 표준 헤더를 보유  
- 요청 유형: API 키
- 요청 버전: 서로 다른 버전의 클라이언트로부터 요청을 받아 각각의 버전에 맞는 응답
- Correlation ID: 각 요청에 붙는 고유한 식별자
- 클라이언트 ID: 요청을 보내는 애플리케이션 식별자
