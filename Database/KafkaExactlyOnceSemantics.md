# 정확히 한 번 의미 구조
최소 한 번 전달의 경우 메시지 중복의 가능성이 여전히 존재  
대부분의 애플리케이션들은 중복 메시지를 제거할 수 있도록 메시지에 고유한 식별자를 포함  
카프카의 정확히 한 번 의미 구조는 멱등적 프로듀서와 트랜잭션 의미 구조의 조합으로 구성  

<br>

## 멱등적 프로듀서
동일한 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질  

<br>

### 멱등적 프로듀서 작동 원리
멱등적 프로듀서 기능 활성화시 모든 메시지는 고유한 프로듀서 ID(`PID`)와 시퀀스 넘버를 보유  
대상 토픽 및 파티션과 해당 두 값을 합치면 각 메시지의 고유한 식별자로 변환  
브로커가 이전에 받은 메시지를 또 받게 될 경우 적절한 에러를 발생  
만약 브로커가 예상보다 높은 시퀀스 넘버를 받으면 `out of order sequence number` 에러 발생  
해당 에러가 발생한 경우 프로듀서와 브로커 사이에 메시지 유실이 발생한 것을 의미  

<br>

1. 프로듀서 재시작  
  프로듀서 장애 발생시 보통 새 프로듀서를 생성해서 장애 난 프로듀서를 대체  
  중요한 점은 프로듀서가 시작될 때 멱등적 프로듀서 기능이 켜져 있을 경우 새로운 PID를 브로커로부터 생성 받음  

2. 브로커 장애  
  컨트롤러는 장애가 난 브로커가 리더를 맡고 있었던 파티션들에 대해 새 리더를 선출  
  팔로워 레플리카는 리더로부터 새로운 메시지를 복제할 때마다 인메모리 버퍼에 최근 저장된 5개의 시퀀스 넘버를 업데이트  
  팔로워가 리더가 된 시점에는 이미 메모리 안에 최근 5개의 시퀀스 넘버를 보유  

<br>

### 멱등적 프로듀서 한계
카프카의 멱등적 프로듀서는 프로듀서 내부 로직으로 인한 재시도가 발생한 경우 생기는 중복만 방지  
동일한 메시지를 가지고 `producer.send()`를 두 번 호출하면 멱등적 프로듀서가 개입하지 않는 만큼 중복 발생  
프로듀서 예외를 잡아서 애플리케이션 로직으로 재시도하는 것보다 프로듀서 자체 재시도 메커니즘을 사용하는 것을 권장  
하나의 인스턴스에서 여러 프로듀서를 띄우는 애플리케이션에서 동일한 메시지 전송시 멱등적 프로듀서는 중복을 잡지 못함  
즉 멱등적 프로듀서는 프로듀서 자체 재시도 메커니즘에 의한 중복 만을 방지  

<br>

### 멱등적 프로듀서 사용법
`enable.idempotence=true` 설정을 추가하면 끝  
- PID를 받아오기 위해 프로듀서 시동 과정에서 API 추가 호출
- 전송되는 모든 레코드 배치에는 PID와 배치 내 첫 메시지의 시퀀스 넘버 포함
- 브로커들은 모든 프로듀서 인스턴스에서 들어온 레코드 배치의 시퀀스 넘버를 검증해서 메시지 중복 방지
- 장애 발생하더라도 각 파티션에 쓰여지는 메시지들 순서 보장

<br>

## 트랜잭션
트랜잭션 기능은 카프카 스트림즈를 사용해서 개발된 애플리케이션에 정확성을 보장하기 위해 도입  
그런 만큼 스트림 처리 애플리케이션의 기본 패턴인 읽기-처리-쓰기 패턴에서 사용하도록 개발  

<br>

### 트랜잭션이 해결하는 문제
원본 토픽으로부터 이벤트를 읽어서 처리한 후 결과를 다른 토픽에 쓰는 경우 아래 문제 발생 가능  
1. 애플리케이션 크래시로 인한 재처리
2. 좀비 애플리케이션에 의해 발생하는 재처리

<br>

정확히 한 번 처리라 함은 읽기, 처리, 쓰기 작업이 원자적으로 이루어진다는 것을 의미  
읽어 온 원본 메시지의 오프셋이 커밋되고 결과가 성공적으로 쓰여지거나 아니면 둘 다 안 일어나거나를 보장  
이런 동작을 지원하기 위해 카프카 트랜잭션은 원자적 다수 파티션 쓰기 기능(`atomic multiplartition write`)을 도입  
오프셋을 커밋하는 것이나 결과를 쓰는 것이 둘 다 파티션(출력 토픽, `_consumer_offsets`)에 메시지를 쓰는 과정을 수반한다는 점에서 착안  

<br>

원자적 다수 파티션 쓰기를 수행하려면 트랜잭션적 프로듀서를 필수로 사용  
보통 프로듀서와의 차이점이란 `transactional.id` 설정이 잡혀 있고 `initTransactions()` 초기화 호출 여부  
PID와는 달리 `transactional.id` 설정은 프로듀서 설정의 일부이며 재시작해도 값이 유지  
브로커는 두 설정의 대응 관계를 유지, 이미 존재하는 트랜잭션적 프로듀서가 초기화 호출을 다시 하면 이전에 쓰던 PID 할당  

<br>

좀비 인스턴스가 중복 프로듀서 생성을 방지하기 위해서는 좀비 펜싱(`zombie fencing`) 필요  
가장 일반적인 좀비 펜싱 방법인 에포크를 사용하는 방식 사용  
초기화 메서드 호출 시 `transactional.id`에 해당하는 에포크 값을 증가  
같은 `transactional.id`를 보유하고 있지만 에포크 값이 낮은 프로듀서의 요청은 FencedProducer 에러 발생
